1 · What UniFFI is

UniFFI is a tool from Mozilla (born out of the Firefox/Application-Services effort to ship one Rust core to iOS, Android, and desktop) that auto-generates the FFI glue needed to call a Rust library from other languages. You write your logic once in Rust, describe the interface, and UniFFI emits:

  • a Rust "scaffolding" layer — the extern "C" entry points compiled into your crate, and
  • idiomatic bindings in each target language that call those entry points for you.

Officially supported targets: KotlinSwiftPythonRuby. Additional targets exist as external bindings generators — including Go (see §9), C#, Kotlin-Multiplatform, and Dart.

2 · The problem it solves

Calling Rust from another language always has to cross a C ABI — that is the only calling convention every runtime agrees on. Hand-writing that boundary means manually authoring #[no_mangle] extern "C" functions, raw-pointer marshalling, string/array encoding, error codes, and a matching set of unsafe declarations on the other side. It is repetitive, easy to get subtly wrong, and must be re-done for every language.

UniFFI's bet: that glue is mechanical, so generate it. One interface description → correct, consistent glue for N languages, regenerated automatically whenever the API changes.

3 · How you define an interface

There are two ways to tell UniFFI about your API. Modern projects favor proc-macros; the original mechanism is a UDL file.

a) Proc-macro mode (current)

Annotate the real Rust directly — no separate file:

// lib.rs
#[derive(uniffi::Record)]
pub struct DirEntry { pub name: String, pub size: u64 }

#[derive(uniffi::Object)]
pub struct Filesystem { /* … */ }

#[uniffi::export]
impl Filesystem {
  pub fn list_directory(&self, path: String)
      -> Result<Vec<DirEntry>, DppError> { /* … */ }
}

uniffi::setup_scaffolding!();

b) UDL mode (original)

A WebIDL-like schema file, kept in sync with the Rust:

// dpp.udl
dictionary DirEntry {
  string name;
  u64 size;
};

interface Filesystem {
  [Throws=DppError]
  sequence<DirEntry> list_directory(string path);
};

Pulled in via uniffi::include_scaffolding!("dpp") in build.rs.

Either way, UniFFI builds an internal component-interface metadata model (records, enums, objects, functions, errors, their types) that drives all code generation.

4 · The build pipeline

End to end, here is what runs and what it produces:

┌─ Rust crate ───────────────────────────────┐ │ your logic + #[uniffi::export] / .udl │ └───────────────┬─────────────────────────────┘ │ cargo build (proc-macros / build.rs run) ▼ ① SCAFFOLDING compiled into your cdylib/staticlib (the extern "C" symbols + a metadata blob) │ │ uniffi-bindgen generate (reads the metadata) ▼ ② FOREIGN BINDINGS source files, one set per language Kotlin .kt Swift .swift Python .py Go .go │ ▼ ③ app imports the bindings; at runtime they dlopen / link the cdylib and call ①

So there are two generated artifacts: (1) the C-ABI surface inside your compiled Rust library, and (2) the per-language wrapper source that knows how to call it. Both come from the same metadata, which is why they never drift.

5 · Scaffolding — the Rust C-ABI layer

The scaffolding is ordinary (generated) Rust that UniFFI compiles into your crate. For each exported function it emits a #[no_mangle] pub extern "C" shim that:

  • takes only C-ABI-safe parameters (integers, floats, pointers, and RustBuffer — see §6);
  • lowers each argument from its FFI form back into the real Rust type;
  • calls your actual function inside a catch_unwind guard (a Rust panic must never unwind across the boundary);
  • lifts the return value back into an FFI form and writes any error into an out-param status struct.

It also exports housekeeping symbols: a per-type free function, allocators for RustBuffer, a checksum/contract-version symbol so a mismatched binding refuses to load, and (in proc-macro mode) the metadata the generator reads. You never see or hand-edit this code.

6 · RustBuffer & the FfiConverter trait

Scalars (i32, f64, …) cross the boundary directly. Everything compound — strings, structs (records), enums, sequences, maps, optionals — is serialized into bytes and passed as a RustBuffer: a small { ptr, len, capacity } struct describing a Rust-allocated byte buffer.

The encoding is defined by the FfiConverter trait (and Lift/Lower/Read/Write helpers). Each side implements the same wire format:

TypeWire encoding
i32 / u64 / f64 …passed by value, no buffer
Stringlength-prefixed UTF-8 in a RustBuffer
record (struct)fields written back-to-back in declaration order
enumu32 variant discriminant, then that variant's fields
Option<T>1 flag byte, then T if present
sequence<T> / mapi32 count, then each element encoded in turn
object (interface)an opaque handle, not serialized — see §7
Why this matters for memory safety: the foreign side never dereferences Rust's struct layout. It reads a byte stream with a known grammar and a length it was given. There is no pointer-chasing into Rust's heap for data — only the handle for objects.

7 · Objects, handles & memory management

Records are passed by value (copied through a RustBuffer). Objects (anything with methods and identity — e.g. a Filesystem or Pipeline) are passed by reference as an opaque handle: the foreign side holds an integer/pointer it cannot inspect, and every method call passes that handle back to Rust.

Lifetime is reference-counted. The Rust side keeps the object behind an Arc; the scaffolding exposes clone/free symbols. The generated binding wires the object's destructor in the host language to the free symbol:

  • Swift — deinit
  • Kotlin — a Cleaner / explicit .destroy() (and AutoCloseable)
  • Python — __del__ / context manager
  • Go — a runtime.SetFinalizer plus a generated Destroy() method
The one sharp edge: the host GC and Rust's Arc are two separate accountants. UniFFI bridges them, but use-after-Destroy on a handle is the failure mode you still have to respect — the same lifecycle care any handle-based API needs. It is bounded to object handles, not to data.

8 · Errors, callbacks & async

  • Errors — a Rust Result<T, E> where E is a UniFFI error enum becomes a thrown exception (Kotlin/Swift/Python) or an idiomatic error return (Go). The scaffolding writes a status code + serialized error into an out-param; the binding turns it into the host idiom.
  • Callback / foreign-trait interfaces — Rust can call back into host-language code. The host registers a vtable of function pointers; Rust invokes them through the same C ABI. This is how you'd pass, say, a progress callback or a host-provided reader.
  • Async — newer UniFFI supports async fn across the boundary by integrating the host's event loop with a Rust future poller. (Go support for async lags the core; verify before relying on it.)

9 · The Go story — uniffi-bindgen-go

Go is not an officially-maintained target. It is served by an external generator, NordSecurity/uniffi-bindgen-go, which plugs into UniFFI as a custom bindings backend. Practical realities:

  • It emits Go source that talks to the scaffolding via CGO — i.e. it generates exactly the import "C" / cgo glue you'd otherwise hand-write, plus typed Go structs for your records and Destroy()-bearing wrappers for your objects.
  • It is version-pinned: each release supports a specific uniffi-rs version. You must keep the generator, the runtime, and your crate's UniFFI dependency in lockstep.
  • You still ship a compiled Rust cdylib/staticlib per target platform and link it with CGO — the packaging story is the same as a hand-written binding.
Key honesty point for our decision: UniFFI-for-Go does not remove CGO or the C ABI. It generates the same unsafe boundary you'd otherwise write by hand — the value is that the unsafe is machine-generated and uniform, not that it disappears.

10 · Does it preserve Rust's memory safety?

This is the question that actually matters for dpp, whose selling point is a memory-safe Apple-format parser. Precise answer:

What is preserved
  • 100% of your core logic stays safe Rust — the parsers never become unsafe.
  • Compound data crosses as a length-checked byte grammar, not raw struct pointers.
  • The hand-written unsafe surface is ~zero: the glue is generated and shared across every consumer of UniFFI.
  • Panics are caught at the boundary, not unwound into the host.
What is not magically guaranteed
  • The C ABI itself is still unsafe by nature — UniFFI generates that unsafe, it does not eliminate it.
  • Two memory managers (host GC + Rust Arc) coexist; use-after-Destroy of a handle is still possible from host misuse.
  • You trust the generator's correctness instead of your own.

If the requirement is a hard memory boundary — where even a hypothetical Rust bug cannot touch Go's address space — no in-process FFI (UniFFI or hand-written) achieves that, because they share an address space by definition. That guarantee only comes from process isolation (a subprocess/IPC daemon) or a WASM sandbox (compile dpp to wasm32-wasi, run it under a wasm runtime). Those trade performance and ergonomics for a true isolation wall. UniFFI's actual claim is narrower and still valuable: minimize and standardize the unavoidable unsafe, and keep every line of your real logic safe.
